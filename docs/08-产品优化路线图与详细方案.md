## 一、调研结论摘要

### 1.1 行业共性问题

| 问题 | 行业表现 | 本系统现状 |
|---|---|---|
| 到期即瘫痪 | 前台半夜弹「注册码过期」，客人等在走廊；授权到期从技术故障变成服务事故 | ✅ 已有到期告警/续期工作台/离线宽限，**缺到期前客户侧主动提醒** |
| 换机/重装丢授权 | 三班倒前台换电脑就要重买授权或找厂家迁移；客服工单第一大来源 | ⚠️ 设备绑定已有，换机要走服务商后台人工处理 |
| 一码多装/试用滥用 | 一套软件装五台；试用码上闲鱼 | ✅ 设备数上限已有，缺异常检测 |
| 防护过度误伤 | 激进指纹+强制在线，VM 迁移/重装就误判换机，正版用户流失 | ⚠️ 离线宽限已有，**无时间回拨防护**（客户端改系统时间可续命） |
| 人工台账失控 | 忘提醒续费、不知激活几台、续期/扩容全靠 Excel | ✅ 后台已有，**缺客户自助续期与闲置盘点** |
| 合同计价打架 | 按房/按人/按并发说不清，员工共用账号毁审计 | ⚠️ 仅按设备数上限，**License 无模块/配额位** |
| 续期靠销售 | 收入漏在「到期没人跟」上 | ⚠️ 自动续期开关已有，**缺支付联动与流失预测** |

### 1.2 最佳实践共识（采纳原则）

1. **服务端发牌 + 本地验签**：元数据在服务端，客户端只验签（Ed25519 ✅ 已具备）
2. **自助优于人工**：换机解绑、续期付费让客户自己完成 → 砍掉 80% 客服工单
3. **防分享不防好人**：激活上限 + 异常检测 + 人工复核，不做硬锁；宁可漏过也不误伤
4. **许可与支付联动**：订阅自动到期、付费即续期，收入不漏
5. **运营化**：用激活/心跳数据驱动续期（谁快到期、谁在流失、谁闲置），从「卖软件」到「运营授权」

### 1.3 本系统已有能力盘点（不重复建设）

设备指纹激活（Ed25519+JWT）｜心跳与离线宽限｜设备数上限（Hotel.max_devices / License.max_devices）｜到期告警与续期工作台｜自动续期开关（Hotel.auto_renew）｜集团总端批量续期｜吊销（含原因）｜操作日志审计｜企微推送（告警/每日汇报）｜三档套餐（Plan.features JSON）｜AI 风控与大模型管道

## 三、P0-1 · 客户端自助换机 / 解绑旧设备

### 3.1 背景与目标

**问题**：酒店前台电脑 3~5 年一换，或重装系统后设备指纹变化，当前要联系服务商后台处理（查旧设备→解绑→重激活），是最集中的售后工单。行业数据：自助解绑可砍掉大半客服量。

**目标**：酒店管理员在客户端内自助完成「换机迁移」，服务商后台可审计、可风控，全程 ≤2 分钟、不发工单。

### 3.2 用户场景

| 场景 | 现状 | 目标 |
|---|---|---|
| 前台换新电脑 | 联系服务商，人工查旧设备解绑 | 客户端「设备管理」一键解绑旧设备 → 新机直接激活 |
| 重装系统（指纹变化） | 当成新设备占配额，旧设备成僵尸 | 老机器客户端识别「同名设备指纹变化」→ 自助迁移 |
| 设备配额满，加新机 | 联系服务商扩容或清僵尸 | 配额满时自助停用 30 天无心跳的设备，或提示扩容 |
| 集团换机 | 总端也做不了 | 集团总端可为旗下门店执行换机（走同一风控） |

### 3.3 功能需求

1. **设备管理页（客户端）**
   - 列出本酒店全部激活设备：名称 / OS / 指纹摘要（后 8 位）/ 最后心跳时间 / 在线状态
   - 每台设备行内操作：`解绑`（危险操作，二次确认）
   - 解绑规则：
     - 仅能解绑**非本机**设备；本机不可解绑自己（只能退出激活）
     - 仅能解绑**离线 ≥30 分钟**的设备（在线设备不可解绑，防误操作拆了正在用的机器）
     - 配额已满时，界面置顶提示可解绑的僵尸设备（离线 ≥30 天优先标注）
   - 解绑后：Device.status=`已解绑`、Hotel.devices 计数 -1、AuditLog 落一条（谁/哪台/何时/来源 IP）

2. **同名迁移（重装系统场景）**
   - 新机激活时客户端带 `device_name`（默认取计算机名）；若同 hotel_id 下存在**同名但指纹不同**的离线设备（离线 ≥30 分钟），激活响应返回 `migration_hint=true`
   - 客户端提示：「检测到疑似重装的旧设备『前台-01』，是否替换？」→ 确认后服务端将旧设备标记 `已迁移`、新设备直接占用其位
   - 冲突保护：同名设备**在线**则不提示迁移（说明是两台真实机器，走正常配额）

3. **风控约束（防自助能力被滥用）**
   - 单酒店每日自助解绑/迁移 ≤3 次，超出报 429 并提示联系服务商
   - 每次解绑/迁移生成 Alert（等级「中」，规则「自助换机」），进风控明细供复核；同一酒店 7 天内 ≥3 次自动升级「高」告警并企微推送
   - 操作全部落 AuditLog（hotel_id、operator、target_device、fingerprint、time、ip）

4. **后台配套**
   - 客户详情-设备清单 Tab：增加「解绑来源」列（自助/服务商后台），被自助解绑的设备保留记录（软删，status 区分，不物理删除）
   - 风控规则表追加一条：「频繁自助换机」

### 3.4 界面与交互

- **客户端**：现有页签结构（激活/状态/通知）增加「设备」页签（或并入「状态」页为设备管理卡片）；危险操作用红色按钮 + 二次确认弹窗（输入设备名最后 2 位确认？——评审点 E1）
- **后台**：客户详情设备清单加列 + 风控规则加行；无新页面

### 3.5 数据模型与接口改动

**模型**（models.py）：
- `Device` 增列：`unbound_at`（String(32)，解绑时间）、`unbound_by`（String(16)：`self`/`admin`/`migration`）
- `Device.status` 取值扩展：`在线 / 离线 / 已解绑 / 已迁移`（现有数据兼容，旧记录默认）

**接口**（client_api.py，`/api/client` 前缀）：
- `GET /devices` — 设备列表（client token 作用域 = 本酒店）
- `POST /devices/unbind` — body `{device_id}`；校验：非本机、离线 ≥30min、日限 3 次；返回 `{ok, quota_left_today}`
- `POST /activate` 扩展 — 请求带 `device_name`；响应新增 `migration_hint`（bool）与 `migrate_target`（旧设备摘要）；`POST /devices/migrate` — body `{old_device_id}` 执行替换
- 后台（main.py）：`DELETE /api/hotels/{hid}/devices/{did}` 保留为服务商通道（现有能力对齐新 status 语义）

### 3.6 安全与边界

- 解绑接口仅 client token（绑定 hotel_id）可调，杜绝跨店解绑；服务端二次校验目标设备归属
- 「离线 ≥30 分钟才可解绑」防止在用机器被拆；时区统一 UTC 存储、北京时间展示（沿用 _fmt_bj 约定）
- 软删保留完整痕迹，支持审计追溯与误操作回滚（后台可「恢复设备」——评审点 E2，建议做）

### 3.7 测试要点

- 解绑成功/在线设备拒绝/本机拒绝/跨店拒绝/日限 3 次第 4 次 429
- 迁移提示仅同名+离线出现；同名在线不提示
- 解绑后配额立即释放，新机能激活；AuditLog/Alert 落库且企微推送给服务商（≥3 次/7 天升级「高」）
- 集团总端为门店换机走同一风控并记录操作人

### 3.8 工作量估计

后端 2~3 天（接口+风控+迁移逻辑）｜客户端 2~3 天（设备页签+迁移提示）｜后台 0.5 天（列+规则）｜测试 1 天。**合计约 6~7 人天**，含一次客户端发版（与 P1-1 合并发）。

## 四、P0-2 · 续期自助化（在线支付 + 凭证兜底）

### 4.1 背景与目标

**问题**：当前续期走「服务商后台手工续期」或自动续期开关（无支付联动），收入依赖销售人工跟进，到期没人跟就漏收。

**目标**：酒店管理员在客户端/集团总端自助完成续期付费；支付成功自动延长 expire_at；对公转账等场景保留「上传凭证+人工确认」兜底。全程留痕、可对账。

### 4.2 用户场景

| 场景 | 流程 |
|---|---|
| 门店自助续期 | 客户端到期前 30 天出现「立即续期」入口 → 选时长（1 年/2 年）→ 微信支付 → 支付回调延 expire_at → 客户端自动刷新状态 |
| 集团批量续期 | 集团总端勾选多家门店 → 生成合并订单 → 一次支付 → 各门店分别延期 |
| 对公转账 | 选「对公汇款」→ 展示收款信息 → 上传回单照片/单号 → 后台「待确认续期」队列人工确认到账后延期 |
| 自动续期 | 已开 auto_renew 的客户：到期前 7 天自动发起扣款（签约代扣，若支付渠道支持）或自动出待付订单+企微提醒 |
| 续期即升级 | 续期页可选换套餐（基础→专业/旗舰），按差价/全价计费（评审点 E3） |

### 4.3 功能需求

1. **续期订单模型**：订单号、hotel_id/group_id、时长、金额、套餐、渠道（wxpay/transfer）、状态机：
   `待支付 → 已支付 → 已生效`；`待支付 → 已关闭（超时 2h）`；`待支付 → 待确认（凭证上传）→ 已生效/已驳回`
2. **支付渠道**（评审点 E4 —— 需要你确认商户号方案）：
   - **方案 A（推荐）**：微信支付（服务商 JSAPI/Native 扫码），支付回调验签后订单置「已支付」并触发续期生效
   - **方案 B（兜底，必做）**：对公转账凭证 + 后台人工确认（不依赖支付资质，先行上线）
   - 建议先上 B、预留 A 的接口位（`payment_provider` 字段），支付资质下来后接 A
3. **生效逻辑**（复用现有续期口径）：`expire_at = max(今天, 现 expire_at) + 时长`；License.type=`续期` 落一条授权记录（沿用现有续期工作台的记录方式）；AuditLog + 企微推送给服务商「XX 酒店自助续期 ¥X 到 YYYY-MM-DD」
4. **客户端到期提醒增强**（配合 1.1「到期即瘫痪」痛点）：
   - 到期前 30/15/7/1 天，客户端「状态」页顶部横幅提醒（颜色随临近度加深）
   - 到期前 7 天起，企微消息推送（若该酒店配置了通知）：文案含「点此查看续期」
   - 已过期：客户端进入只读/宽限模式（沿用离线宽限机制），横幅「已过期，立即续期恢复」
5. **对账**：订单导出 CSV（时间/酒店/金额/渠道/状态/经办）；后台「续期订单」列表页（P0 与订单模型同批进）

### 4.4 界面与交互

- **客户端**：「状态」页卡片底部 `立即续期` 按钮（仅到期前 30 天/已过期出现）→ 续期弹层（时长选择、价格表、支付方式、二维码/凭证上传）
- **集团总端**：门店一览勾选 → 批量续期按钮升级为「批量下单支付」（保留原一键续期作为服务商代操作入口）
- **后台**：新增「续期订单」页（筛选：状态/渠道/时间），待确认队列支持「确认到账/驳回（填原因）」；客户详情加订单历史折叠区

### 4.5 数据模型与接口改动

**新模型 `RenewOrder`**：`id / order_no / target_type(hotel|group) / target_id / plan / months / amount / channel / status / pay_proof(凭证 URL) / paid_at / confirmed_by / created_at`

**接口**：
- client_api：`POST /renew/order`（创建订单）、`GET /renew/order/{no}`（查状态轮询）、`POST /renew/order/{no}/proof`（传凭证）
- main.py：`GET/POST /api/renew-orders`（后台列表/确认）、支付回调 `POST /api/pay/notify`（方案 A 预留）
- 现有 `POST /api/client/group/renew` 改造为：批量生成订单（服务商代续期保留原语义，加 `via=backend` 标记）

### 4.6 安全与边界

- 金额一律服务端计算，客户端只展示（防篡改）；订单与 hotel 绑定，token 校验归属
- 支付回调验签（方案 A）；凭证上传限图片 ≤5MB、病毒扫描可后置
- 超时未支付自动关单；重复支付幂等（同一订单重复回调只生效一次）
- 价格来自 Plan.yearly_price（已有字段），改动价走后台套餐管理

### 4.7 测试要点

- 订单状态机全路径（含超时关单、重复回调幂等、驳回重传）
- 生效边界：续期从「原到期日」顺延而非从支付日；已过期续期从今天起算
- 批量续期部分失败的回滚语义（全部生效或全部不动——建议全有全无）
- 对账导出与 AuditLog/企微推送核对

### 4.8 工作量估计

后端 3~4 天（订单模型+状态机+回调+对账）｜客户端 2~3 天（续期弹层+横幅提醒+凭证上传）｜后台 2 天（订单页+确认队列）｜支付渠道接入 1~2 天（视资质）｜测试 1.5 天。**合计约 10~12 人天**（不含支付资质审批时间）。

## 五、P1-1 · 时间回拨防护

### 5.1 背景与目标

客户端本地校验 expire_at 时，改系统时间即可「续命」。行业共识：签名令牌 + 单调时间证据 + 服务端时间锚点。

### 5.2 方案（客户端 Rust license-core 为主）

1. **服务端时间锚点**：每次 heartbeat/profile 响应带 `server_time`（协议已有 server_time 字段约定，**勿改语义**），客户端持久化 `last_server_time` 与本地时间对照
2. **回拨检测**：本地当前时间 < `last_seen_local_time - 2min`（且 < `last_server_time` 容差）→ 判定时间回拨
3. **处置策略（宽严相济）**：
   - 回拨幅度 ≤24h：提示「系统时间异常，请校正」，功能降级不锁死（防误伤虚拟机时钟漂移）
   - 回拨 >24h 或连续 3 次检测到：进入只读模式，需联网心跳一次（对齐 server_time）恢复
4. **开机单调证据**：记录「最大见过的本地时间」单调递增推进（只增不减），配合心跳间隔合理性（相邻心跳间隔 > 心跳周期 ×0.5 才计数），回拨后心跳不会被当成正常推进
5. **免责边界**：不追求强对抗（防的是随手改时间，不是专业破解）；NTP 校正等正常回拨（≤2min 容差）不触发

### 5.3 数据与接口

- 无需新表；客户端本地持久化 `mono_last_seen` / `last_server_time`
- heartbeat 响应确认携带 `server_time`（client_api 已有约定，回归确认即可）
- 后台风控：心跳异常（时间戳倒退）→ Alert 规则「时间异常」（挂 P1-2 的告警通道）

### 5.4 测试要点

- 改系统时间 +1 天/-3 天/反复横跳各场景的提示与恢复
- 虚拟机挂起恢复后的时钟漂移不误伤（≤2min 容差）
- 联网一次心跳即恢复只读

### 5.5 工作量估计

客户端 2 天（license-core）｜服务端 0.5 天（确认 server_time + 告警）｜测试 0.5 天。**约 3 人天**，随 P0-1 同一客户端发版。

## 六、P1-2 · 异常激活告警

### 6.1 背景与目标

一码多装/授权倒卖的特征是异常激活模式。已有 8 条风控规则 + 企微告警链路，本项是**加规则 + 加检测**，成本低见效快。

### 6.2 检测规则（风控规则表 +1）

| 规则 | 阈值（可配 settings） | 等级 | 动作 |
|---|---|---|---|
| 激活速度异常 | 同酒店 ≥5 台/24h | 高 | Alert + 企微推服务商 |
| 设备更替频繁 | 同酒店 ≥3 次解绑/迁移/7 天（与 P0-1 联动） | 中→高 | Alert，连续触发升「高」 |
| 指纹复用 | 同一指纹激活 ≥2 个酒店 | 紧急 | Alert + 企微 + 建议吊销待人工 |
| 僵尸复活 | 离线 ≥90 天设备突然心跳 | 中 | Alert（可能是授权转卖） |
| 到期后仍活跃 | status=已过期但心跳持续 | 中 | Alert + 企微（关联 P0-2 续期提醒） |

### 6.3 实现要点

- 复用 Alert 模型与聚合/明细视图，无需新表；检测点挂在 activate/heartbeat/unbind 现有路径上（轻量规则函数，同步判定）
- 阈值进 settings（`risk_*` 键），后台安全设计页可调（沿用现有配置模式）
- 告警走既有 push_message 三路路由；**不自动吊销**（人工复核原则），仅「指纹复用」建议人工吊销
- 处置闭环沿用 Alert.handled_by/handle_note

### 6.4 测试要点

- 每条规则正/反例；阈值可配生效；企微推送内容含酒店/规则/证据摘要
- 聚合视图按新规则正确聚合计数

### 6.5 工作量估计

后端 2 天（规则函数+检测点+配置）｜前端 0.5 天（规则表展示）｜测试 1 天。**约 3.5 人天**。

## 七、P1-3 · License 模块/配额位（计价单元可配置）

### 7.1 背景与目标

行业第一合同纠纷是「计价单元说不清」。现在只有 max_devices 一个配额；本项让 License 携带**功能模块位 + 多维配额**，支撑按房量/按模块/按并发卖，合同怎么签系统怎么表达。

### 7.2 方案

1. **License/Plan 增配额与模块**（评审点 E5 —— 哪些模块拆分卖需要你定）：
   - 配额：`max_devices`（已有）/ `max_rooms`（按房量计价）/ `max_concurrent`（并发数，预留）
   - 模块位：`features` JSON（Plan.features 已有此约定，扩展为 License 级覆盖）——候选模块：`ai_risk`（AI 风控）/ `report`（报表）/ `group_portal`（集团总端）/ `api`（API 对接）/ `push`（企微推送）
2. **下发与执行**：
   - `license_payload_for()`（client_api.py 已有）扩展输出 `features` + `quotas`，客户端启动/心跳刷新
   - 客户端按模块位开关功能入口（未授权模块灰置 +「升级套餐解锁」引导 → 直连 P0-2 续期升级）
3. **管理端**：发放授权弹窗加模块勾选与配额输入；套餐管理三档卡片编辑默认模块组合
4. **超限策略**：设备超限沿用现有拒绝；房间数/并发超限**先告警不锁**（90 天过渡期，观察误伤）——评审点 E6

### 7.3 数据模型与接口

- `License` 增列：`features`（Text，JSON 字符串，默认取 Plan.features）、`max_rooms`（Integer，默认 0=不限）
- `Plan.features` 从展示文案升级为结构化 JSON（含 label/enabled 两维，兼容现有前台展示）
- `license_payload_for` 响应加 `features`/`quotas`；`POST /api/licenses`（发放）请求加对应字段

### 7.4 测试要点

- 模块位关闭时客户端功能入口灰置、升级引导正确
- License 级覆盖 Plan 级默认值；旧数据无 features 字段时行为不变（全开兼容）
- 配额告警不误伤（max_rooms=0 表示不限）

### 7.5 工作量估计

后端 2 天（模型+下发+发放）｜客户端 1.5 天（功能开关）｜后台 1 天（发放弹窗/套餐卡）｜测试 1 天。**约 5.5 人天**。

## 八、P2-1 · 授权盘点报表（闲置/超装/重复指纹）

### 8.1 背景与目标

集团续约谈判需要数据：哪些授权闲置、哪些超装、哪些指纹可疑。行业经验：20~40% 的软件支出可从盘点中找回。对服务商则是**沉睡收入挖掘**工具。

### 8.2 报表内容（后台「授权盘点」页或总览新卡片）

| 指标 | 口径 | 行动引导 |
|---|---|---|
| 闲置授权 | 生效中但 ≥30 天无任何心跳 | 企微提醒客户/标记「待回访」 |
| 半闲置 | 设备利用率 <30%（活跃设备/配额） | 续期时建议降配或缩配额（省客户钱促信任） |
| 超装嫌疑 | P1-2「指纹复用」/「激活速度」命中 | 转风控复核 |
| 临近到期分布 | 7/30/60/90 天（已有）+ 按集团聚合 | 续期工作台联动 |
| 空壳门店 | 集团下 0 设备且 0 心跳的门店 | 集团总端提示清理 |

### 8.3 实现要点

- 数据全部来自现有 Device/Hotel/Alert/心跳字段（last_active），纯查询聚合，无新表
- 导出 CSV（复用现有导出模式）；每月 1 日企微自动推服务商「月度盘点摘要」（挂进 push_daily 服务端汇报的月度变体）
- 客户详情加「活跃度」小指标（近 30 天心跳天数）

### 8.4 工作量估计

后端 2 天（聚合查询+导出+月度推送）｜前端 2 天（报表页）｜测试 1 天。**约 5 人天**（依赖 P1-2 数据）。

## 九、P2-2 · AI 续费预测与主动续期

### 9.1 背景与目标

用使用行为预测流失，把「到期提醒」升级为「流失预警 + 主动出击」。差异化卖点：同价位竞品少有。

### 9.2 方案

1. **信号（全部已有数据）**：近 30 天心跳天数环比、活跃设备数趋势、告警量趋势、是否开自动续期、历史续期延迟天数、剩余天数
2. **流失分**（规则打分先行，模型可后置）：
   - 剩余 <30 天 × 使用率环比降 >50% → 高流失风险
   - 剩余 <7 天 × 未支付订单 × 无心跳 >7 天 → 紧急
   - 输出：`renewal_risk`（低/中/高/紧急）+ 主要因子
3. **动作**：
   - 续期工作台按流失分排序（高风险置顶）+ 显要标注
   - 企微推送（服务商/集团）：「3 家高流失风险门店，建议本周内跟进」+ 明细
   - 客户端侧对高风险酒店自动出现「限时续期优惠」横幅位（价格策略留运营配置，不写死）
4. **AI 增强**（接现有大模型管道，llm-logs 留痕）：
   - 「生成续期跟进话术」按钮：基于该酒店画像（套餐/使用率/告警）生成一段企微跟进文案，运营复制发送
   - 模型失败降级为模板文案（沿用数据接地+完整性兜底原则，**数字一律来自数据直出**）

### 9.3 数据与接口

- 无新表；Hotel 加计算字段或查询时实时算 `renewal_risk`
- `GET /api/hotels/page` 响应加 `renewal_risk` 列（排序可选）；`POST /api/ai/renew-script`（话术生成，走审计网关）
- push_daily 新增「周度流失预警」推送（复用调度线程，settings 键 `push_risk_weekly`）

### 9.4 工作量估计

后端 3 天（评分+接口+推送）｜前端 1.5 天（排序/标识/话术按钮）｜AI 接入 1 天｜测试 1 天。**约 6.5 人天**。

## 十、明确不做的事（防过度设计）

- ❌ 强制在线验证（always-online）——离线场景（酒店弱网）是刚需，离线宽限已是正确路线
- ❌ 硬件加密狗——增加物流成本，不适合桌面 SaaS 形态
- ❌ 激进设备指纹（多因子硬件 ID）——VM 迁移/重装误伤，行业已证明支持成本大于收益；现有单指纹 + 自助迁移是更优解
- ❌ 自动吊销——一切处置人工复核，防误伤正版
- ❌ 自研复杂 DRM/代码混淆——把工程力放在**体验与运营**上，防护以「防随手分享」为限
